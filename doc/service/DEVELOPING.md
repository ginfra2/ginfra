# Notes on developing services for Ginfra

## Requirements.

While using the generates services will support all the ginfra features and meet all these requirements, 
but you don't actually have to do this.
The ginfra app needs only one this to handle your services.  It will look for a file in the service root directory
or if in a container, it will look for it in the root (/) directory.  The fill must be called specifics.json and
it looks like this:

```
{
   "meta": {
      "version": 1,
      "name": "giuser",
      "type": "apiecho",
      "module_name": "gitlab.com/ginfra/gservices/service_giuser",
      "serviceclass": "giuser",
      "invocationcmd": ""
   }
}
```

Name, type and serviceclass are required.  Only version 1 is supported.  Name and serviceclass can be and usually
are the same.  Module_name is only used by the generator, so if it isn't generated by Ginfra, you can ignore it.

'Invocationcmd' tells ginfra to use a command other than the default to start the service locally (like on your laptop and 
not in a container).  If not set, it will try to run a script named start_local.sh or start_local.cmd, depending on
if your system is unix/linux/etc or windows.  So create the script if you want ginfra to be able to start your service
this way.

For containers, it will just let the natural entrypoint start it, which is completely up to you.

The specifics.json file and actually tell ginfra to do additional things.  Read the [specifics documentation](Specifics.md) for
additional information.

## Service configuration

During startup, ginfra was drop a file called service_config.json either in your service root directory or if in a 
container, it will put it in the root (/) directory or in a directory called /config.   Look for it in both places.
The file will look like this:

``` 
{
   "auth": "WZ9SAQDB8TX2UJQBQ1SD",
   "config_access_token": "XVEWHJLSUQUS",
   "config_portal_uri": "http://nodedocker:5111",
   "config_uri": "http://172.18.0.2:5111",
   "deployment": "default",
   "id": "89594d52383f",
   "name": "giuser",
   "port": 8902,
   "specifics": {
      "user_provider": "file:///service/test/userfile.json"
   },
   "type": "host"
}
```

There are go functions to load this file in gitlab.com/ginfra/ginfra/common/service/shared module.  For java
it is best to check out the [gipet service](https://gitlab.com/ginfra/gservices/-/tree/main/service_gipet?ref_type=heads) for an example.

Again, doing anything with this is completely optional, but the generated applications use it all.  heck them out for 
examples for how to use it, but below has a little more information on the fields.

- auth: This is a token that the ginfra application will use to authenticate itself with the service control api.
- config_access_token: This is the access token used to talk to the configuration provider.
- config_uri: Location of the configuration provider if everything is on a local network (i.e. pc and docker)
- config_portal_uri: Portal location for the configuration provider if accessing it though a managed service (i.e. kubernetes)
- deployment: What deployment the service belongs to.
- name: Name of the service, which should just be the name from the specifics.json file.
- port: The port of the main API service.  
- type: 'local' for process on local system, 'host' for local container and 'kube' for kubernetes container.
- specifics: Additional information provided to the service during invocation.  This information can be sent through the ginfra command line.
